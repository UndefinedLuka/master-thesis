\chapter{Results}
\label{ch:results}

This chapter presents the results of the experiments described in chapters \ref{ch:methodolgy} and
\ref{ch:implementation}. We first establish
experiment coverage and serialization efficiency, and then evaluate Direct Context Inference and Text-to-SQL
in terms of retrieval accuracy and operational efficiency. We also examine the influence of model and database
size and evaluate the effectiveness and cost of SQL error correction.

Figures and tables report pointwise \qty{95}{\percent} confidence intervals using the database-level bootstrap
described in Section~\ref{sec:confidence-intervals}. Error bars describe uncertainty in the reported
estimates. Paired effect sizes and their intervals are reported in the accompanying text as
differences or ratios relative to an explicit reference. Exact experiment counts remain descriptive.
Comparisons are exploratory;
the ordering of observed means alone does not establish a reliable ranking of configurations.

\section{Experiment coverage}

All experiments were run on the FRIDA high-performance computing cluster using the Slurm workload scheduler.
Each experiment was assigned a dedicated NVIDIA H100 GPU, which kept the hardware conditions consistent
across models. The experiment campaign produced runs for Qwen~3.5 (0.8B, 2B, 4B, 9B, and 27B),
Ministral~3 (8B and 14B), and Gemma~4 (E2B, E4B, 12B, and 26B-A4B).

The Qwen~3.5 27B runs were excluded from the analysis because the model did not consistently delimit its
reasoning trace. Consequently, the final answer could not be separated reliably from the thinking trace for
answer-level evaluation. The results reported in this chapter therefore cover the remaining ten models.

We evaluated the development splits of Spider and BIRD. Spider contains \num{1034} questions associated with \num{20}
databases, while BIRD contains \num{1534} questions associated
with \num{11} databases. This gives a total of \num{2568} questions across \num{31} databases.

For every model and question, the direct-context pipeline was evaluated with six serialization formats: JSON,
XML, YAML, CSV, Markdown, and TOON. The same questions were also evaluated with the Text-to-SQL pipeline,
which received the database schema and generated an SQL query. Each model therefore had seven possible runs
per question: six direct-context runs and one Text-to-SQL run.

Before analysing accuracy, we separate completed runs from runs that ended in an error. The unit in
Table~\ref{tab:experiment-outcomes} is one run---a question evaluated with one model and one method---rather
than one unique question. A successful run means that the pipeline produced an answer; it does not imply that
the answer was correct. We distinguish runs that completed without a recorded error from Text-to-SQL runs
that succeeded after SQL error correction. Failed runs are grouped into context-window overflow, an SQL
execution error that remained after the retry limit, failure to extract an SQL statement, and any other recorded error.

Of the \num{179760} retained runs, \num{110185} (\qty{61.3}{\percent}) produced an answer and \num{69575} (\qty{38.7}{\percent}) failed. The success
rate was \qty{87.6}{\percent} for Spider and \qty{43.6}{\percent} for BIRD. Context-window overflow accounted for \num{67536} failures
(\qty{97.1}{\percent} of all failed runs), while \num{1984} runs ended with an SQL execution error after the retry limit and \num{55}
failed because no SQL statement could be extracted. The SQL correction loop recovered a further \num{1357} runs
that had failed on an earlier attempt; no model-generation, malformed-direct-output, or other terminal errors
were recorded.

\section{Serialization efficiency}

This section examines only the tokens required to represent the database contents. Prompt instructions,
questions, chat-template tokens, and output-token headroom are excluded, allowing us to isolate the overhead
introduced by each serialization format. Token counts were measured for every database with one representative
tokenizer from each of the Qwen~3.5, Ministral~3, and Gemma~4 families. The resulting data therefore contain
\num{558} measurements: \num{31} databases, six formats, and three tokenizer families.

\input{../code/analysis/tables/serialization_efficiency}

Table~\ref{tab:serialization-efficiency} reports the arithmetic mean across all databases and tokenizer
families within each dataset. The relative value is calculated separately for Spider and BIRD, using
CSV as the baseline. Brackets report confidence intervals for the means and paired
ratios. CSV required the fewest tokens in both datasets.
TOON was close to this baseline, requiring only \num{1.04}$\times$ as many tokens for Spider and \num{1.03}$\times$ for
BIRD, while Markdown required \num{1.22}$\times$ and \num{1.09}$\times$, respectively. The more verbose hierarchical
formats had substantially greater overhead. Compared with CSV, XML required \num{3.24}$\times$ as many tokens for
Spider and \num{2.40}$\times$ for BIRD; JSON required \num{2.46}$\times$ and \num{1.68}$\times$, and YAML required
\num{1.90}$\times$ and \num{1.49}$\times$.

Mean token counts describe overall serialization overhead, but database sizes vary substantially and a small
number of very large databases can strongly influence the arithmetic mean. The mean also does not show how
many individual databases can be processed within the fixed context window.
The same table therefore counts
database payloads containing no more than \num{131072} tokens for each tokenizer family. For Spider, CSV and TOON
both fit \num{19} of \num{20} databases, while the other formats fit \num{18}. The distinction was larger for BIRD: CSV and TOON
fit \num{6} of \num{11} databases for every tokenizer family, whereas XML fit only \num{2}. JSON fit \num{3} databases with the
Qwen~3.5 and Gemma~4 tokenizers and \num{4} with Ministral~3. These counts include only the serialized payload, so a
complete prompt close to the limit may still exceed the available context after instructions, the question,
and output headroom are added.

Tokenizer choice also changes the number of tokens assigned to the same text.
Figure~\ref{fig:tokenizer-family-comparison}
compares the three tokenizer families on identical database and format pairs. For every pair, the family with
the fewest tokens defines a zero-percent baseline; points show the median excess over that baseline across

uniformly best across all formats.
Qwen~3.5 was the most efficient for CSV and was close to the best for TOON and YAML, while Ministral~3 was
usually the most efficient for JSON and Markdown and also performed well for XML. Gemma~4 was the most
efficient for Spider TOON, but it incurred the largest median overhead for Spider JSON. Across all paired
measurements, the median excess was \qty{0.23}{\percent} for Ministral~3, \qty{2.15}{\percent} for Qwen~3.5, and \qty{4.81}{\percent} for Gemma~4,
showing that format choice had a much larger effect on token use than tokenizer-family choice in this
experiment.

Using Qwen~3.5 as a fixed reference, the median paired CSV token-count ratio for Ministral~3
was \num{1.056} on Spider (\qty{95}{\percent} interval: \numrange{1.054}{1.063}) and \num{1.050} on BIRD (\numrange{1.036}{1.069}).
For JSON, the corresponding ratios were \num{0.912} (\numrange{0.897}{0.925}) and \num{0.916} (\numrange{0.907}{0.956}).
Thus, Ministral~3 used about \qtyrange{5}{6}{\percent} more tokens for CSV but about \qtyrange{8}{9}{\percent} fewer for JSON,
illustrating that the tokenizer advantage depended on the format.

\section{Direct Context Inference}

In the Direct Context Inference pipeline, the model answers each question using database contents placed
directly in its prompt. We examine this pipeline from three perspectives: retrieval accuracy, operational
efficiency, and the influence of database size.

\subsection{Retrieval accuracy}

Retrieval accuracy was evaluated using NEM, BERTScore, and ROUGE-L, as defined in
Section~\ref{sec:reference-answer-metrics}. These scores describe reference-answer agreement rather than
independently verified correctness; BERTScore is reported as raw F1. The reported means include all
direct-context runs from the ten retained models, including runs assigned a score
of zero after failing the pre-inference context-limit check. The results therefore represent
end-to-end effectiveness under the fixed \num{128}K-token limit, rather than accuracy conditional on the model
having produced an answer. Each Spider format summarizes \num{10340} runs, while each BIRD format summarizes
\num{15340} runs.

\begin{figure}[htb]
  \centering
  \includegraphics[width=\textwidth]{../code/analysis/figures/direct_accuracy_by_format.pdf}
  \caption{Mean direct-context retrieval accuracy by serialization format (NEM, raw BERTScore F1,
    and ROUGE-L F1). Each bar includes all questions
    and all ten retained models for the named dataset. Failed runs retain zero scores. Whiskers
  show pointwise \qty{95}{\percent} confidence intervals.}
  \label{fig:direct-accuracy-by-format}
\end{figure}

Figure~\ref{fig:direct-accuracy-by-format} compares the six serialization formats. On Spider, TOON achieved
the highest NEM (\num{0.178}), CSV the highest BERTScore (\num{0.815}), and CSV the highest ROUGE-L (\num{0.340}).
The raw BERTScore means separate compact CSV and TOON (\num{0.8154} and \num{0.8148}) from the other formats, which
range from \num{0.717} for XML to \num{0.720} for Markdown; CSV exceeds XML by \num{0.098}. NEM and ROUGE-L are more
closely grouped, with best-to-worst differences of \num{0.014} and \num{0.032}, respectively. Thus, no format is
uniformly best on Spider, but CSV and TOON remain among the strongest across the three metrics.

The paired intervals show the uncertainty behind this ordering. On Spider, TOON exceeded CSV
by \num{0.23} percentage points in NEM, with a \qty{95}{\percent} interval from \num{-0.81} to
\num{1.29} percentage points. XML was \num{1.10} percentage points below CSV, with an interval from
\num{-2.67} to \num{0.68}. Both intervals include zero, so the observed ordering does not establish a
clear accuracy advantage for these comparisons.

The separation between formats was clearer on BIRD. CSV achieved the highest values for NEM,
BERTScore, and ROUGE-L (\num{0.090}, \num{0.424}, and \num{0.109}), with TOON close behind (\num{0.087}, \num{0.424}, and
\num{0.106}). XML produced the lowest values (\num{0.041}, \num{0.169}, and \num{0.052}). The CSV-to-XML ratio is about \num{2.5} for
BERTScore and about \num{2} for NEM and ROUGE-L. This ordering is consistent with the context-fit results in
Table~\ref{tab:serialization-efficiency}:
compact formats allowed more BIRD databases to enter the model context, whereas verbose formats produced more
zero-scored context failures. The observed difference therefore reflects both the model's ability to interpret
a format and the format's ability to represent the database within the available context.

On BIRD, the XML--CSV NEM difference was \num{-4.96} percentage points
(\qty{95}{\percent} interval: \numrange{-9.49}{-1.46}), whereas the TOON--CSV difference was \num{-0.32}
percentage points (\numrange{-0.79}{0.19}). The comparison with Text-to-SQL shows a much
larger pipeline difference: relative to direct CSV, NEM increased by \num{46.96}
percentage points on Spider (\numrange{42.25}{51.98}) and \num{50.78} on BIRD (\numrange{40.72}{61.24}). These paired
comparisons use the complete benchmark, including context-window failures.

Figure~\ref{fig:direct-accuracy-by-model-size} examines the influence of model size. Each point averages one
model's scores across all six formats and all questions, corresponding to \num{6204} Spider runs or \num{9204} BIRD
runs. On Spider, accuracy generally increased with model size in every family. Gemma~4 showed the clearest
trend: from E2B to 26B-A4B, NEM increased from \num{0.138} to \num{0.294}, BERTScore from \num{0.756} to
\num{0.777}, and ROUGE-L from \num{0.302} to \num{0.478}. Qwen~3.5 also improved substantially between 0.8B and 9B, while
the improvement from Ministral~3 8B to 14B was smaller.

The same general relationship was present on BIRD, but at considerably lower score levels. Gemma~4 improved
consistently with size and reached \num{0.095} NEM, \num{0.311} BERTScore, and \num{0.113} ROUGE-L at
26B-A4B. Qwen~3.5 improved steadily in NEM and ROUGE-L, but its BERTScore did not increase
monotonically, and Ministral~3 14B improved over 8B on NEM and ROUGE-L while obtaining a
lower BERTScore. Model scale was therefore beneficial overall, but parameter count alone did not determine
performance; model family and metric also affected the observed trend. The horizontal axis uses the
nominal sizes encoded in the model names;
Gemma~4 26B-A4B is positioned at \num{26}B total parameters even though approximately \num{4}B parameters are active per
token.

Relative to the smallest retained model in each family, the NEM gain on
Spider was \num{15.62} percentage points for Gemma~4 26B-A4B (\qty{95}{\percent} interval: \numrange{10.62}{21.61}),
\num{13.70} for Qwen~3.5 9B (\numrange{9.05}{19.36}), and \num{1.55} for Ministral~3 14B (\numrange{0.14}{2.91}).
The corresponding BIRD gains were \num{5.61} (\numrange{1.69}{10.63}), \num{5.38} (\numrange{1.79}{9.86}), and \num{0.71}
(\num{-0.26} to \num{1.93}) percentage points. The smaller Ministral gain on BIRD remains uncertain.

\subsection{Operational efficiency}

\input{../code/analysis/tables/direct_operational_efficiency}

Operational efficiency was evaluated using the number of input and output tokens, TTFT,
generation time, and total response latency. Output-token counts include reasoning traces and are not split into
reasoning and visible-answer tokens. TTFT is measured from request submission until the first output
token is received. Generation time in this subsection covers the remaining interval from the first token to
completion, while total latency covers the complete request from submission to completion. For Direct Context
Inference there is no subsequent query-execution phase, so total latency is the sum of TTFT and this
post-first-token generation interval.

Unlike the retrieval-accuracy analysis, this comparison cannot include context-window failures because those
runs never reached model inference and consequently have no meaningful timing or token measurements. We
therefore use a common complete-case cohort to keep the workload identical across formats: within each
dataset, a question is retained only if all ten models produced an answer in all six serialization formats.
This leaves \num{852} Spider questions from \num{18} databases and \num{303} BIRD questions from \num{2} databases, corresponding to \num{69300}
model--question--format observations. Every format is consequently evaluated on exactly the same questions and
models within each dataset. The BIRD efficiency results therefore apply only to the two databases represented
in this strict common cohort.

    common complete-case cohort within each dataset: \num{852} Spider questions and \num{303} BIRD questions, evaluated with

Table~\ref{tab:direct-operational-efficiency} reports all five mean measurements.
Figure~\ref{fig:direct-token-usage-by-format}
visualizes input and output token use. Input-token consumption followed the expected ordering from serialization
verbosity. On Spider, CSV required an average of \num{5366} input tokens, followed by TOON with \num{5758} and Markdown
with \num{6779}. XML required \num{20186} tokens, \num{3.76} times the CSV value, while JSON required \num{15296}. The same pattern
was stronger in absolute terms on BIRD: CSV required \num{31756} input tokens, compared with \num{97190} for XML and
\num{76239} for JSON.

Output-token differences were much smaller than input-token differences and did not follow the same strict
ordering. Spider responses ranged from \num{81.2} tokens for CSV to \num{119.6} for YAML, while BIRD responses ranged from
\num{219.6} for TOON to \num{260.5} for YAML. This indicates that the serialization format primarily changes the cost of
providing database context; its effect on answer length is comparatively limited. Because output length also
depends on the model's chosen wording and reasoning trace, these differences should not be interpreted as a
direct measure of answer quality.

The paired XML-to-CSV mean input-token ratio was \num{3.76} on Spider (\qty{95}{\percent} interval: \numrange{2.84}{4.38})
and \num{3.06} on BIRD (\numrange{2.94}{3.20}). TOON was closer to CSV, with ratios of \num{1.07} (\numrange{1.04}{1.12})
and \num{1.03} (\numrange{1.02}{1.04}). For output tokens, YAML-to-CSV ratios were \num{1.47} (\numrange{1.30}{1.57})
and \num{1.17} (\numrange{1.15}{1.21}), respectively. The BIRD intervals describe only the two-database cohort.

Figure~\ref{fig:direct-latency-by-format} decomposes total response latency into TTFT and generation after the
first token. The latency ordering closely followed input-token consumption. For Spider, average total latency
increased from \qty{1.25}{\second} with CSV to \qty{1.37}{\second} with TOON, \qty{1.61}{\second} with Markdown, \qty{3.16}{\second} with
YAML, \qty{4.44}{\second} with JSON, and \qty{7.42}{\second} with XML. BIRD showed the same ordering at a larger scale:
CSV, TOON, and Markdown completed in \qty{8.02}{\second}, \qty{8.27}{\second}, and \qty{8.95}{\second} on average, whereas YAML required \qty{17.15}{\second},
JSON \qty{31.20}{\second}, and XML \qty{50.88}{\second}. The paired XML-to-CSV mean-latency ratio
was \num{5.91} on Spider (\qty{95}{\percent} interval: \numrange{2.24}{8.31}) and \num{6.34} on BIRD (\numrange{6.22}{6.47}).
TOON-to-CSV ratios were \num{1.09} (\numrange{1.04}{1.16}) and \num{1.03} (\numrange{1.028}{1.033}), respectively.

Most of this increase occurred before the first output token. TTFT ranged from \qty{0.78}{\second} for Spider CSV to
\qty{6.45}{\second} for Spider XML, and from \qty{6.32}{\second} for BIRD CSV to \qty{46.87}{\second} for BIRD XML. In contrast,
the post-first-token generation interval ranged from \qtyrange{0.48}{0.97}{\second} on Spider and from \qtyrange{1.70}{4.00}{\second}
on BIRD. The dominant operational cost of verbose formats was therefore processing the larger input
context, not generating the final answer. CSV and TOON offered nearly identical latency, while Markdown
introduced a modest increase and the three hierarchical formats---particularly JSON and XML---incurred a much
larger delay.

\subsection{Influence of database size}

\begin{figure}[htb]
  \centering
  \includegraphics[width=\textwidth]{../code/analysis/figures/direct_accuracy_by_database_size_nem.pdf}
  \caption{Mean Direct Context NEM by effective database size and serialization format. Each
    point represents one database, with point area indicating its number of benchmark questions; separate trend
    lines are fitted for Spider and BIRD. Shading shows pointwise \qty{95}{\percent} bootstrap intervals for the
    fitted mean trend; annotations report Pearson's $r$ and its \qty{95}{\percent} interval. Database size is
    shown on a logarithmic token scale. A correlation interval is unavailable when more than \qty{5}{\percent}
  of bootstrap samples have constant scores.}
  \label{fig:direct-accuracy-by-database-size-nem}
\end{figure}

Figure~\ref{fig:direct-accuracy-by-database-size-nem} presents the NEM view of the final
direct-context analysis, which examines whether retrieval accuracy changes with database size. Within each
format panel, database size is defined as the mean number of tokens required to serialize the complete
materialized database with the three representative tokenizer families. This effective size is more informative
than row count alone because it also captures the number and width of columns, repeated field names, and the
length of textual values. It refers to full Spider databases and to the deterministically sampled BIRD databases
used throughout the experiment.

The analysis produces one candidate figure for each retrieval metric: NEM, BERTScore,
and ROUGE-L. Each figure contains six panels, one for every serialization format, and places all \num{31} Spider
and BIRD databases on the same logarithmic size axis within each panel. A point reports the mean end-to-end
score for one database and format across all associated questions and all ten retained models; its area
indicates the number of associated benchmark questions. Spider and BIRD are distinguished by colour and fitted
with separate least-squares trend lines because their construction and difficulty differ. Keeping the formats
separate avoids hiding differences in both token footprint and context-window feasibility behind one
cross-format average.

Across the complete database sets, accuracy generally decreased as effective database size increased: the
database-level correlations were negative across formats for NEM, BERTScore, and ROUGE-L. The decline
was therefore not specific to strict textual equality or a single similarity measure.

The largest databases also expose the hard context-window limit of direct inference. All runs associated with
five BIRD databases---\texttt{california\_schools}, \texttt{card\_games},
\texttt{codebase\_community}, \texttt{european\_football\_2}, and \texttt{formula\_1}---exceeded the
context window in every format and consequently received zero scores. The same occurred for Spider's
\texttt{wta\_1} database. These structural zeroes contribute to the downward trend. Among databases with at
least one positive score, associations were usually negative, but some remaining samples are too small for
a firm generalization: for example, only two BIRD databases have positive XML scores, and the BIRD YAML NEM
association is a small exception to the negative direction. The results
therefore show both context-window failures and an overall association between larger databases and lower
scores, without establishing a uniform decline among every feasible subset.

Database size should nevertheless not be interpreted as the sole cause of the score differences. Each point
also represents a different domain, schema, data quality, and set of questions, and these factors are not held
constant across databases. The figure therefore describes an empirical association rather than a
controlled causal effect. Within this limitation, the combined Spider and BIRD results show that Direct Context
Inference is most reliable on smaller databases and becomes progressively less suitable as the serialized
payload approaches or exceeds the available context.

\section{Text-to-SQL}

This section evaluates retrieval accuracy and operational efficiency for the \num{25680} retained Text-to-SQL runs.

\subsection{Retrieval accuracy}

Text-to-SQL retrieval was evaluated using NEM, BERTScore, and ROUGE-L on text representations of
the returned and reference rows. Execution success records whether a query ran without
error within the retry limit; it does not establish that the query retrieved the intended information. Failed
SQL runs retain zero text-based scores, so the reported means represent end-to-end pipeline performance rather
than scores conditioned on successful execution.

\input{../code/analysis/tables/text_to_sql_retrieval_accuracy}

Table~\ref{tab:text-to-sql-retrieval-accuracy} summarizes the dataset-level results. On Spider, \qty{95.3}{\percent} of
queries executed successfully; on BIRD, \qty{89.8}{\percent} did so.

The text-based metrics show a similar dataset difference. Spider reached mean scores of \num{0.645} for NEM,
\num{0.918} for BERTScore, and \num{0.705} for ROUGE-L. BIRD reached \num{0.598}, \num{0.861}, and \num{0.373},
respectively. The reduction from Spider to BIRD was much larger for ROUGE-L than for BERTScore, indicating
that sequence-level overlap with the reference rows degraded more sharply than raw embedding-based semantic
similarity. The two metric values are not directly comparable because they use different scoring scales.

\begin{figure}[htb]
  \centering
  \includegraphics[width=\textwidth]{../code/analysis/figures/text_to_sql_accuracy_by_model_size.pdf}
  \caption{Mean Text-to-SQL retrieval accuracy by model size and family (NEM, raw BERTScore F1,
    and ROUGE-L F1). Failed SQL runs retain zero scores,
    and Qwen~3.5 27B is excluded from the analysis. Gemma~4 26B-A4B is positioned by its total nominal parameter
  count. Whiskers show pointwise \qty{95}{\percent} confidence intervals.}
  \label{fig:text-to-sql-accuracy-by-model-size}

Figure~\ref{fig:text-to-sql-accuracy-by-model-size} shows a strong relationship between model size and
text-based agreement scores, particularly within Qwen~3.5. On Spider, Qwen~3.5 NEM increased from
\num{0.292} at \num{0.8}B parameters to \num{0.719} at \num{9}B; on BIRD it increased from \num{0.202} to \num{0.686}. Most of this improvement
occurred between \num{0.8}B and \num{4}B, after which the curve began to flatten. Gemma~4 was the strongest family overall
and improved consistently with size. Its 26B-A4B variant achieved the highest observed scores: \num{0.778}
NEM, \num{0.975} BERTScore, and \num{0.816} ROUGE-L on Spider, and \num{0.745}, \num{0.969}, and \num{0.487} on
BIRD. Ministral~3 improved more modestly between 8B and 14B and remained below similarly sized Gemma~4 models.
These results show that model scale improves the reported retrieval metrics, but architecture remains important
because models of similar nominal size did not achieve equivalent accuracy.

The paired Qwen~3.5 9B-minus-0.8B NEM gain was \num{42.65} percentage points
on Spider (\qty{95}{\percent} interval: \numrange{36.76}{47.85}) and \num{48.44} on BIRD (\numrange{43.50}{54.13}).
For Gemma~4 26B-A4B relative to E2B, the gains were \num{8.61} (\numrange{4.36}{13.02}) and \num{10.69}
(\numrange{5.66}{16.73}) percentage points. Ministral~3 14B relative to 8B showed smaller gains of
\num{2.51} (\num{-0.42} to \num{5.80}) and \num{1.56} (\num{-0.73} to \num{4.01}) percentage points; both intervals include zero.

\subsection{Operational efficiency}

Text-to-SQL operational measurements include every initial generation and correction attempt. Input and output
tokens are accumulated across attempts, as is model-generation time; output counts include any reasoning traces.
The latency decomposition uses the sum of TTFT intervals across attempts, the remaining post-first-token
generation time, and SQL execution time. Total latency therefore includes the model and database time of all
retries. Unlike Direct Context Inference, all Text-to-SQL runs have operational measurements, including those
that exhausted the retry limit.

\input{../code/analysis/tables/text_to_sql_operational_efficiency}

Table~\ref{tab:text-to-sql-operational-efficiency} reports dataset-level means. Spider required \num{802} input and
\num{108.1} output tokens per run, compared with \num{1893} input and \num{219.5} output tokens for BIRD. The larger BIRD values
reflect both more complex schemas and more correction attempts: the mean retry count was \num{0.39}, compared with
\num{0.17} on Spider. Average total latency was consequently \qty{1.06}{\second} for BIRD and \qty{0.54}{\second} for Spider. SQL
execution itself required only \qtyrange{0.008}{0.010}{\second} on average, less than \qty{2}{\percent} of total latency in either dataset;
the main cost remained model inference and repeated generation.

\subsection{Error correction performance}

Under the three-retry policy defined in Section~\ref{sec:minimalist-text-to-sql},
Table~\ref{tab:text-to-sql-error-correction} reports execution-success counts by attempt.

\input{../code/analysis/tables/text_to_sql_error_correction}

Most queries executed without correction. On Spider, \num{9577} of \num{10340} runs (\qty{92.62}{\percent}) succeeded on the first
attempt. A further \num{250} executed on the second attempt, \num{30} on the third, and \num{2} on the fourth. The retry
mechanism therefore recovered executable queries in \num{282} Spider runs. The remaining \num{481} runs (\qty{4.65}{\percent}) failed
completely after all available attempts.

BIRD required correction more frequently. Of \num{15340} runs, \num{12707} (\qty{82.84}{\percent}) executed on the first attempt.
The second, third, and fourth attempts recovered execution for \num{878}, \num{160}, and \num{37} runs, respectively. In total,
retries recovered \num{1075} executable queries, while \num{1558} runs (\qty{10.16}{\percent}) remained complete failures. Considering
only runs that either recovered after a retry or ultimately failed, the mechanism recovered execution in \qty{37.0}{\percent} of
Spider cases and \qty{40.8}{\percent} of BIRD cases.

Relative to stopping after the first attempt, retries increased execution success by \num{2.73}
percentage points on Spider (\qty{95}{\percent} interval: \numrange{1.79}{3.59}) and \num{7.01} on BIRD (\numrange{5.77}{8.44}).
These paired execution-success gains are measured across all runs.

Retries also introduced a measurable operational cost. Attempts after the first added \qty{1850.4}{\second}
(\qty{30.8}{\minute}) of model-generation time on Spider and \qty{7234.3}{\second} (\qty{120.6}{\minute}) on BIRD, or \qty{2.52}{\hour}
across both datasets. Averaged across every run, this corresponds to \num{0.179} additional seconds for Spider and
\qty{0.472}{\second} for BIRD. Among runs that actually entered the correction loop, the mean additional generation
time was \qty{2.43}{\second} for Spider and \qty{2.75}{\second} for BIRD.

The \qty{95}{\percent} interval for mean additional generation time across all runs was \qtyrange{0.078}{0.277}{\second}
on Spider and \qtyrange{0.349}{0.618}{\second} on BIRD.

\section{Text-to-SQL and Direct context inference comparison}
\label{sec:common-cohort-comparison}

To compare operational efficiency without differences in workload, we retain only questions completed by
all ten models in all six direct-context formats and Text-to-SQL. Completion requires an answer without a
pipeline error and, for Text-to-SQL, successful query execution (it does not require a correct answer).
Successful SQL corrections remain included with their accumulated token usage and timing. The shared cohort
contains \num{561} Spider questions from \num{18} databases and \num{121} BIRD questions from \num{2} databases
(\texttt{student\_club} and \texttt{toxicology}), representing \qty{54.3}{\percent} and \qty{7.9}{\percent} of the development
splits. Every method uses identical questions, models, and database contents: full Spider databases and the
same materialized sampled BIRD databases.

For XML relative to Text-to-SQL, the paired mean-latency ratios of \num{22.82} and \num{124.48} had

\section{Summary}

This chapter presented results from \num{179760} retained runs across Spider and BIRD, ten models, six
serialization formats, and the Text-to-SQL pipeline. Serialization had a substantial effect on context use:
CSV required the fewest tokens, TOON remained close to it, and XML was consistently the most verbose. These
differences directly affected context-window coverage and response latency, while tokenizer-family choice had
a comparatively smaller influence on token counts.

For Direct Context Inference, compact formats provided the best overall balance between accuracy and
operational efficiency. CSV and TOON achieved strong retrieval scores and the lowest latency, whereas JSON and
XML frequently exceeded the context window and required considerably more time before producing the first
token. Accuracy generally improved with model size but decreased as the effective database size increased,
showing that direct inference becomes less reliable and less practical as more data must be included in the
prompt.

Text-to-SQL achieved substantially higher scores for text-based agreement with the reference while using a
much smaller schema-based input, and its scores generally improved with model size. Query execution itself
contributed little to total latency; model generation and correction retries accounted for most of the cost. The retry
mechanism recovered \num{1357} otherwise non-executable queries, while failed correction sequences added most of
the retry overhead. Overall, the results demonstrate
that format selection is central to Direct Context Inference, while model capability and reliable SQL generation are the main factors
for Text-to-SQL.

\chapter{Results}
\label{ch:results}

This chapter presents the results of the experiments described in the previous chapters. We first establish
experiment coverage and serialization efficiency, and then evaluate Direct Context Inference and Text-to-SQL
in terms of retrieval accuracy and operational efficiency. We also examine the influence of model and database
size and evaluate the effectiveness and cost of SQL error correction.

\section{Experiment coverage}

All experiments were run on the FRIDA high-performance computing cluster using the Slurm workload scheduler.
Each experiment was assigned a dedicated NVIDIA H100 GPU, which kept the hardware conditions consistent
across models. The experiment campaign produced runs for Qwen~3.5 (0.8B, 2B, 4B, 9B, and 27B),
Ministral~3 (8B and 14B), and Gemma~4 (E2B, E4B, 12B, and 26B-A4B).

The Qwen~3.5 27B runs were excluded from the analysis because the model did not consistently delimit its
reasoning trace. Consequently, thinking tokens could not be separated reliably from the visible output tokens,
which would make its token-use and timing results incomparable with those of the other models. The results
reported in this chapter therefore cover the remaining ten models.

We evaluated the development splits of Spider and BIRD. As summarized in Table~\ref{tab:dataset-coverage},
Spider contains 1,034 questions associated with 20 databases, while BIRD contains 1,534 questions associated
with 11 databases. This gives a total of 2,568 questions across 31 databases.

For every model and question, the direct-context pipeline was evaluated with six serialization formats: JSON,
XML, YAML, CSV, Markdown, and TOON. The same questions were also evaluated with the Text-to-SQL pipeline,
which received the database schema and generated an SQL query. Each model therefore had seven possible runs
per question: six direct-context runs and one Text-to-SQL run.

Before analysing accuracy, we separate completed runs from runs that ended in an error. The unit in
Table~\ref{tab:experiment-outcomes} is one run---a question evaluated with one model and one method---rather
than one unique question. A successful run means that the pipeline produced an answer; it does not imply that
the answer was correct. We distinguish runs that completed without a recorded error from Text-to-SQL runs
that succeeded after SQL error correction. Failed runs are grouped into context-window overflow, an SQL
execution error that remained after the retry limit, failure to extract an SQL statement, model or backend
generation errors, empty or malformed direct outputs, and any other recorded error.

Of the 179,760 retained runs, 110,185 (61.3\%) produced an answer and 69,575 (38.7\%) failed. The success
rate was 87.6\% for Spider and 43.6\% for BIRD. Context-window overflow accounted for 67,536 failures
(97.1\% of all failed runs), while 1,984 runs ended with an SQL execution error after the retry limit and 55
failed because no SQL statement could be extracted. The SQL correction loop recovered a further 1,357 runs
that had failed on an earlier attempt; no model-generation, malformed-direct-output, or other terminal errors
were recorded.

\section{Serialization efficiency}

This section examines only the tokens required to represent the database contents. Prompt instructions,
questions, chat-template tokens, and output-token headroom are excluded, allowing us to isolate the overhead
introduced by each serialization format. Token counts were measured for every database with one representative
tokenizer from each of the Qwen~3.5, Ministral~3, and Gemma~4 families. The resulting data therefore contain
558 measurements: 31 databases, six formats, and three tokenizer families.

Table~\ref{tab:serialization-average-tokens} reports the arithmetic mean across all databases and tokenizer
families within each dataset. The relative value is calculated separately for Spider and BIRD, using the format
with the lowest mean token count as the $1.00\times$ baseline. CSV required the fewest tokens in both datasets.
TOON was close to this baseline, requiring only $1.04\times$ as many tokens for Spider and $1.03\times$ for
BIRD, while Markdown required $1.22\times$ and $1.09\times$, respectively. The more verbose hierarchical
formats had substantially greater overhead. Compared with CSV, XML required $3.24\times$ as many tokens for
Spider and $2.40\times$ for BIRD; JSON required $2.46\times$ and $1.68\times$, and YAML required
$1.90\times$ and $1.49\times$.

\input{../code/analysis/tables/serialization_average_tokens}

Mean token counts describe overall serialization overhead, but database sizes vary substantially and a small
number of very large databases can strongly influence the arithmetic mean. The mean also does not show how
many individual databases can be processed within the fixed context window. Table~\ref{tab:serialization-database-fit} therefore counts
database payloads containing no more than 131,072 tokens for each tokenizer family. For Spider, CSV and TOON
both fit 19 of 20 databases, while the other formats fit 18. The distinction was larger for BIRD: CSV and TOON
fit 6 of 11 databases for every tokenizer family, whereas XML fit only 2. JSON fit 3 databases with the
Qwen~3.5 and Gemma~4 tokenizers and 4 with Ministral~3. These counts include only the serialized payload, so a
complete prompt close to the limit may still exceed the available context after instructions, the question,
and output headroom are added.

Tokenizer choice also changes the number of tokens assigned to the same text. Figure~\ref{fig:tokenizer-family-comparison}
compares the three tokenizer families on identical database and format pairs. For every pair, the family with
the fewest tokens defines a zero-percent baseline; points show the median excess over that baseline across
databases, and whiskers show the interquartile range. No tokenizer was uniformly best across all formats.
Qwen~3.5 was the most efficient for CSV and was close to the best for TOON and YAML, while Ministral~3 was
usually the most efficient for JSON and Markdown and also performed well for XML. Gemma~4 was the most
efficient for Spider TOON, but it incurred the largest median overhead for Spider JSON. Across all paired
measurements, the median excess was 0.23\% for Ministral~3, 2.15\% for Qwen~3.5, and 4.81\% for Gemma~4,
showing that format choice had a much larger effect on token use than tokenizer-family choice in this
experiment.

\section{Direct Context Inference}

In the Direct Context Inference pipeline, the model answers each question using database contents placed
directly in its prompt. We examine this pipeline from three perspectives: retrieval accuracy, operational
efficiency, and the influence of database size.

\subsection{Retrieval accuracy}

Retrieval accuracy was evaluated using Normalized Exact Match, BERTScore~F1, and ROUGE-L~F1. Normalized
Exact Match measures whether the generated and reference answers are equal after text normalization,
BERTScore measures their semantic similarity, and ROUGE-L measures their longest-subsequence overlap. The
reported means include all direct-context runs from the ten retained models, including runs assigned a score
of zero because the serialized database exceeded the context window. The results therefore represent
end-to-end effectiveness under the fixed 128K-token limit, rather than accuracy conditional on the model
having produced an answer. Each Spider format summarizes 10,340 runs, while each BIRD format summarizes
15,340 runs.

Figure~\ref{fig:direct-accuracy-by-format} compares the six serialization formats. The Spider results were
closely grouped: TOON achieved the highest Normalized Exact Match (0.178), Markdown the highest BERTScore~F1
(0.211), and CSV the highest ROUGE-L~F1 (0.340). XML had the lowest mean for all three metrics, but the
absolute difference between the best and worst formats remained limited to 0.014 for Normalized Exact Match,
0.019 for BERTScore~F1, and 0.032 for ROUGE-L~F1. Consequently, no format was uniformly best on Spider,
although the compact CSV and TOON representations remained among the strongest across the three metrics.

The separation between formats was clearer on BIRD. CSV achieved the highest values for Normalized Exact
Match, BERTScore~F1, and ROUGE-L~F1 (0.090, 0.057, and 0.109), with TOON close behind (0.087, 0.053, and
0.106). XML produced the lowest values (0.041, 0.029, and 0.052), approximately half of the corresponding CSV
scores. This ordering is consistent with the context-fit results in Table~\ref{tab:serialization-database-fit}:
compact formats allowed more BIRD databases to enter the model context, whereas verbose formats produced more
zero-scored context failures. The observed difference therefore reflects both the model's ability to interpret
a format and the format's ability to represent the database within the available context.

Figure~\ref{fig:direct-accuracy-by-model-size} examines the influence of model size. Each point averages one
model's scores across all six formats and all questions, corresponding to 6,204 Spider runs or 9,204 BIRD
runs. On Spider, accuracy generally increased with model size in every family. Gemma~4 showed the clearest
trend: from E2B to 26B-A4B, Normalized Exact Match increased from 0.138 to 0.294, BERTScore~F1 from 0.234 to
0.357, and ROUGE-L~F1 from 0.302 to 0.478. Qwen~3.5 also improved substantially between 0.8B and 9B, while
the improvement from Ministral~3 8B to 14B was smaller.

The same general relationship was present on BIRD, but at considerably lower score levels. Gemma~4 improved
consistently with size and reached 0.095 Normalized Exact Match, 0.103 BERTScore~F1, and 0.113 ROUGE-L~F1 at
26B-A4B. Qwen~3.5 improved steadily in Normalized Exact Match and ROUGE-L, but its BERTScore did not increase
monotonically, and Ministral~3 14B improved over 8B on Normalized Exact Match and ROUGE-L while obtaining a
lower BERTScore. Model scale was therefore beneficial overall, but parameter count alone did not determine
performance; model family and metric also affected the observed trend. BERTScore was calculated with baseline
rescaling, so the negative values visible for Qwen~3.5 0.8B indicate similarity below that baseline rather
than an invalid negative probability. The horizontal axis uses the nominal sizes encoded in the model names;
Gemma~4 26B-A4B is positioned at 26B total parameters even though approximately 4B parameters are active per
token.

\subsection{Operational efficiency}

Operational efficiency was evaluated using the number of input and output tokens, time to first token (TTFT),
generation time, and total response latency. TTFT is measured from request submission until the first output
token is received. Generation time in this subsection covers the remaining interval from the first token to
completion, while total latency covers the complete request from submission to completion. For Direct Context
Inference there is no subsequent query-execution phase, so total latency is the sum of TTFT and this
post-first-token generation interval.

Unlike the retrieval-accuracy analysis, this comparison cannot include context-window failures because those
runs never reached model inference and consequently have no meaningful timing or token measurements. We
therefore use a common complete-case cohort to avoid survivorship bias: within each dataset, a question is
retained only if all ten models produced an answer in all six serialization formats. This leaves 852 Spider
questions from 18 databases and 303 BIRD questions from 2 databases, corresponding to 69,300
model--question--format observations. Every format is consequently evaluated on exactly the same questions and
models within each dataset, although the BIRD efficiency results apply only to the two databases represented in
this strict common cohort.

Table~\ref{tab:direct-operational-efficiency} reports all five mean measurements. Figure~\ref{fig:direct-token-usage-by-format}
visualizes input and output token use. Input-token consumption followed the expected ordering from serialization
verbosity. On Spider, CSV required an average of 5,366 input tokens, followed by TOON with 5,758 and Markdown
with 6,779. XML required 20,186 tokens, 3.76 times the CSV value, while JSON required 15,296. The same pattern
was stronger in absolute terms on BIRD: CSV required 31,756 input tokens, compared with 97,190 for XML and
76,239 for JSON.

Output-token differences were much smaller than input-token differences and did not follow the same strict
ordering. Spider responses ranged from 81.2 tokens for CSV to 119.6 for YAML, while BIRD responses ranged from
219.6 for TOON to 260.5 for YAML. This indicates that the serialization format primarily changes the cost of
providing database context; its effect on answer length is comparatively limited. Because output length also
depends on the model's chosen wording and reasoning trace, these differences should not be interpreted as a
direct measure of answer quality.

6.45 seconds for Spider XML, and from 6.32 seconds for BIRD CSV to 46.87 seconds for BIRD XML. In contrast,
the post-first-token generation interval ranged from 0.48 to 0.97 seconds on Spider and from 1.70 to 4.00
seconds on BIRD. The dominant operational cost of verbose formats was therefore processing the larger input
context, not generating the final answer. CSV and TOON offered nearly identical latency, while Markdown
introduced a modest increase and the three hierarchical formats---particularly JSON and XML---incurred a much
larger delay.

\subsection{Influence of database size}

The final direct-context analysis examines whether retrieval accuracy changes with database size. Within each
format panel, database size is defined as the mean number of tokens required to serialize the complete
materialized database with the three representative tokenizer families. This effective size is more informative
than row count alone because it also captures the number and width of columns, repeated field names, and the
length of textual values. It refers to full Spider databases and to the deterministically sampled BIRD databases
used throughout the experiment.

The analysis produces one candidate figure for each retrieval metric: Normalized Exact Match, BERTScore~F1,
and ROUGE-L~F1. Each figure contains six panels, one for every serialization format, and places all 31 Spider
and BIRD databases on the same logarithmic size axis within each panel. A point reports the mean end-to-end
score for one database and format across all associated questions and all ten retained models; its area
indicates the number of associated benchmark questions. Spider and BIRD are distinguished by colour and fitted
with separate least-squares trend lines because their construction and difficulty differ. Keeping the formats
separate avoids hiding differences in both token footprint and context-window feasibility behind one
cross-format average.

Accuracy decreased as effective database size increased for every metric in both datasets. Although the exact
correlation varied by format, the direction of the fitted relationship was consistently negative across the
candidate figures. The decline was visible for Normalized Exact Match, BERTScore~F1, and ROUGE-L~F1, showing
that the association is not specific to either strict textual equality or a single similarity measure.

The largest databases also expose the hard context-window limit of direct inference. All runs associated with
five BIRD databases---\texttt{california\_schools}, \texttt{card\_games},
\texttt{codebase\_community}, \texttt{european\_football\_2}, and \texttt{formula\_1}---exceeded the
context window in every format and consequently received zero scores. The same occurred for Spider's
\texttt{wta\_1} database. These structural zeroes contribute to the downward trend, but they do not explain it
entirely: among databases with at least one positive score, the association remained negative. This suggests
that increasing context size affects direct inference in two stages: first by making some databases impossible
to process within the fixed window, and then by making retrieval more difficult even when at least part of the
experiment remains feasible.

Database size should nevertheless not be interpreted as the sole cause of the score differences. Each point
also represents a different domain, schema, data quality, and set of questions, and these factors are not held
constant across databases. The figure therefore establishes a strong empirical association rather than a
controlled causal effect. Within this limitation, the combined Spider and BIRD results show that Direct Context
Inference is most reliable on smaller databases and becomes progressively less suitable as the serialized
payload approaches or exceeds the available context.

\section{Text-to-SQL}

In the Text-to-SQL pipeline, the model receives the database schema and generates an SQL query instead of
reading serialized table contents directly. The query is executed against the same database used to construct
the reference answer, and execution errors can be returned to the model for up to three correction attempts.
This section evaluates retrieval accuracy and operational efficiency for the 25,680 retained Text-to-SQL runs.

\subsection{Retrieval accuracy}

Text-to-SQL retrieval was evaluated in three complementary ways. First, the rows returned by the generated
query were converted into a stable textual representation and compared with the reference rows using
Normalized Exact Match, BERTScore~F1, and ROUGE-L~F1. Second, execution success records whether a query ran
without error within the retry limit, irrespective of whether it returned the correct data. Finally, result
match records whether the executed query returned the same rows as the reference query. Failed SQL runs retain
zero text-similarity scores, so the reported means represent end-to-end pipeline accuracy rather than accuracy
conditioned on successful execution.

Table~\ref{tab:text-to-sql-retrieval-accuracy} summarizes the dataset-level results. On Spider, 95.3\% of
queries executed successfully, but only 65.8\% of all runs returned the correct result. BIRD was more difficult:
89.8\% executed successfully and 58.5\% returned the correct rows. Among queries that did execute, this
corresponds to correct-result rates of approximately 69.0\% for Spider and 65.1\% for BIRD. Successful execution
was therefore necessary but not sufficient for correctness; many syntactically valid queries selected the
wrong tables, columns, conditions, or aggregations.

The text-based metrics show a similar dataset difference. Spider reached mean scores of 0.645 for Normalized
Exact Match, 0.744 for BERTScore~F1, and 0.705 for ROUGE-L~F1. BIRD reached 0.598, 0.675, and 0.373,
respectively. The reduction from Spider to BIRD was much larger for ROUGE-L than for BERTScore, indicating
that sequence-level overlap with the reference rows degraded more sharply than embedding-based semantic
similarity. The two metric values are not directly comparable because they use different scoring scales.

\input{../code/analysis/tables/text_to_sql_retrieval_accuracy}

Figure~\ref{fig:text-to-sql-accuracy-by-model-size} shows a strong relationship between model size and
retrieval quality, particularly within Qwen~3.5. On Spider, Qwen~3.5 Normalized Exact Match increased from
0.292 at 0.8B parameters to 0.719 at 9B; on BIRD it increased from 0.202 to 0.686. Most of this improvement
occurred between 0.8B and 4B, after which the curve began to flatten. Gemma~4 was the strongest family overall
and improved consistently with size. Its 26B-A4B variant achieved the highest observed scores: 0.778
Normalized Exact Match, 0.852 BERTScore~F1, and 0.816 ROUGE-L~F1 on Spider, and 0.745, 0.819, and 0.487 on
BIRD. Ministral~3 improved more modestly between 8B and 14B and remained below similarly sized Gemma~4 models.
These results show that model scale substantially improves SQL generation, but architecture remains important
because models of similar nominal size did not achieve equivalent accuracy.

\subsection{Operational efficiency}

Text-to-SQL operational measurements include every initial generation and correction attempt. Input and output
tokens are accumulated across attempts, as is model-generation time. The latency decomposition uses the sum of
time-to-first-token intervals across attempts, the remaining post-first-token generation time, and SQL
execution time. Total latency therefore captures the full cost of retries rather than only the final successful
query. Unlike Direct Context Inference, all Text-to-SQL runs have operational measurements, including those
that exhausted the retry limit.

Table~\ref{tab:text-to-sql-operational-efficiency} reports dataset-level means. Spider required 802 input and
108.1 output tokens per run, compared with 1,893 input and 219.5 output tokens for BIRD. The larger BIRD values
reflect both more complex schemas and more correction attempts: the mean retry count was 0.39, compared with
0.17 on Spider. Average total latency was consequently 1.06 seconds for BIRD and 0.54 seconds for Spider. SQL
execution itself required only 0.008--0.010 seconds on average, less than 2\% of total latency in either dataset;
the main cost remained model inference and repeated generation.

Figure~\ref{fig:text-to-sql-token-usage} shows that token consumption varied more by model than by dataset
alone. The smallest Qwen~3.5 models were clear outliers. On BIRD, Qwen~3.5 0.8B used an average of 5,155 input
and 1,205 output tokens, while Qwen~3.5 2B used 2,789 and 325. In contrast, most models of 4B or more used
approximately 1,200--1,700 input tokens and 67--109 output tokens. The same pattern appeared on Spider at a
smaller scale. These differences do not result only from tokenizer choice: the smallest Qwen models generated
longer responses and triggered substantially more correction attempts.

counts by producing valid SQL on the first attempt and generating fewer tokens. Operational efficiency in the
Text-to-SQL pipeline was therefore determined by both per-token inference speed and query-generation
reliability.

\subsection{Error correction performance}

When a generated query fails to execute, the pipeline returns the database error to the model and requests a
corrected query. Up to three retries are allowed after the initial generation, giving each run a maximum of
four attempts. This mechanism can respond to detectable failures such as invalid syntax, nonexistent tables or
columns, and responses from which no SQL statement can be extracted. It cannot identify a semantically wrong
query that executes successfully, because no database error is produced. Consequently, an attempt reported as
successful in this subsection means that its query executed; Table~\ref{tab:text-to-sql-error-correction}
reports correct-result counts separately.

Most queries executed without correction. On Spider, 9,577 of 10,340 runs (92.62\%) succeeded on the first
attempt, of which 6,705 returned the correct result. A further 250 executed on the second attempt, 30 on the
third, and 2 on the fourth; their corresponding correct-result counts were 82, 15, and 0. The retry mechanism
therefore recovered executable queries in 282 Spider runs, but only 97 of those recovered runs returned the
reference rows. The remaining 481 runs (4.65\%) failed completely after all available attempts.

BIRD required correction more frequently. Of 15,340 runs, 12,707 (82.84\%) executed on the first attempt and
8,464 returned the correct result. The second, third, and fourth attempts recovered execution for 878, 160,
and 37 runs, respectively, with 436, 59, and 13 correct results. In total, retries recovered 1,075 executable
queries and 508 correct results, while 1,558 runs (10.16\%) remained complete failures. Considering only runs
that either recovered after a retry or ultimately failed, the mechanism recovered execution in 37.0\% of
Spider cases and 40.8\% of BIRD cases. These results show that database feedback was useful, but that execution
recovery did not guarantee semantic correctness.

\input{../code/analysis/tables/text_to_sql_error_correction}

Retries also introduced a measurable operational cost. Attempts after the first added 1,850.4 seconds
(30.8 minutes) of model-generation time on Spider and 7,234.3 seconds (120.6 minutes) on BIRD, or 2.52 hours
across both datasets. Averaged across every run, this corresponds to 0.179 additional seconds for Spider and
0.472 seconds for BIRD. Among runs that actually entered the correction loop, the mean additional generation
time was 2.43 seconds for Spider and 2.75 seconds for BIRD.

Figure~\ref{fig:text-to-sql-error-correction} shows where this cost arose. The first retry added 658.9 seconds
of aggregate model time on Spider and 2,725.1 seconds on BIRD. The second added 594.0 and 2,287.6 seconds, and
the third added 597.6 and 2,221.6 seconds. Although progressively fewer runs reached each stage, later
attempts were longer on average because their prompts included the original exchange and preceding error
feedback. Complete failures accounted for 95.2\% of all retry-generation time on Spider and 89.4\% on BIRD,
because these runs necessarily consumed every permitted attempt without producing an executable query.

The reported overhead is the exact additional model-generation time recorded for attempts two through four.
Per-attempt SQL execution times were not persisted separately, so the small amount of database execution time
caused specifically by retries cannot be isolated and is excluded from this calculation. The aggregate
Text-to-SQL measurements show that SQL execution represented less than 2\% of total latency, but the retry-time
values should nevertheless be interpreted as model-generation overhead rather than complete end-to-end retry
latency.

\section{Summary}

This chapter presented results from 179,760 retained runs across Spider and BIRD, ten models, six
serialization formats, and the Text-to-SQL pipeline. Serialization had a substantial effect on context use:
CSV required the fewest tokens, TOON remained close to it, and XML was consistently the most verbose. These
differences directly affected context-window coverage and response latency, while tokenizer-family choice had
a comparatively smaller influence on token counts.

For Direct Context Inference, compact formats provided the best overall balance between accuracy and
operational efficiency. CSV and TOON achieved strong retrieval scores and the lowest latency, whereas JSON and
XML frequently exceeded the context window and required considerably more time before producing the first
token. Accuracy generally improved with model size but decreased as the effective database size increased,
showing that direct inference becomes less reliable and less practical as more data must be included in the
prompt.

Text-to-SQL achieved substantially higher retrieval accuracy while using a much smaller schema-based input,
and its performance generally improved with model size. Query execution itself contributed little to total
latency; model generation and correction retries accounted for most of the cost. The retry mechanism recovered
1,357 otherwise non-executable queries, but many recovered queries still returned incorrect results, and failed
correction sequences added most of the retry overhead. Overall, the results demonstrate that format selection
is central to Direct Context Inference, while model capability and reliable SQL generation are the main factors
for Text-to-SQL.

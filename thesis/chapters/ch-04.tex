\chapter{Implementation}
\label{ch:implementation}

This chapter describes how the experimental design introduced in Chapter~\ref{ch:methodolgy} is implemented
end to end. We will cover the infrastructure, model selection (selection criteria), result evaluation, and
test reproducibility.

\section{Computational Infrastructure}

All experiments are executed on the FRIDA \cite{ulfri_rdc} high-performance computing cluster operated by the
Research Data
Centre at the Faculty of Computer and Information Science, University of Ljubljana. FRIDA is
managed by the Slurm workload scheduler, which provides GPU allocation and walltime-based job
preemption. The primary compute target is a single NVIDIA H100 GPU with \qty{80}{\giga\byte} of high-bandwidth memory, which
provides sufficient capacity to hold even the largest quantized model (\num{27} billion parameters) entirely in GPU
memory while maintaining a \num{128}K-token key--value (KV) cache.

\subsection{Container Environment}

FRIDA does not expose a traditional module system. Instead, all software environments are packaged as Enroot
containers managed through the Pyxis Slurm plugin. Our container image is based on the NVIDIA GPU Cloud image
\texttt{pytorch:25.06-py3}, which provides CUDA, cuDNN, and Python~3.12 out of the box. On top of this base
image, we add \texttt{llama.cpp}. The scoring dependencies (PyTorch,
Transformers, rouge-score, bert-score) are co-installed as optional package extras. The
fully built container is exported as a squashfs image (\texttt{.sqsh}).

\section{Model Selection and Quantization}

We evaluate three families of open-weight instruction-tuned language models, chosen to span a wide parameter
range while remaining recent enough to reflect current architectural advances:

\begin{itemize}
  \item \textbf{Ministral~3} \cite{liu2026ministral} - available at \num{3}B, \num{8}B, and \num{14}B parameters.
    This family uses a sliding-window attention mechanism and is optimized for low-latency deployment.
  \item \textbf{Qwen~3.5} \cite{yang2025qwen3} - available at \num{0.8}B, \num{2}B, \num{4}B, \num{9}B, and \num{27}B
    parameters. Qwen~3.5 models feature hybrid thinking capabilities with explicit reasoning traces enclosed
    in \texttt{<think>} blocks.
  \item \textbf{Gemma~4} \cite{gemmateam2026gemma4technicalreport} - a recently released family of lightweight open
    models designed for efficient on-device and server-side deployment.
\end{itemize}

Together, these three families give us eleven distinct model sizes ranging from sub-\num{1}B to \num{27}B parameters,
enabling fine-grained analysis of the relationship between model scale and information extraction accuracy.

\subsection{Quantization Strategy}

All models are served in the GGUF format \cite{llamacpp} using the \textbf{Q4\_K\_M} quantization
scheme. Q4\_K\_M belongs to the k-quant family introduced in the \texttt{llama.cpp} \cite{llamacpp}
ecosystem, which applies mixed-precision quantization: most weight tensors are stored at \num{4}-bit precision,
while attention key/value projection matrices and the output head retain higher precision (\num{6}-bit).

We choose Q4\_K\_M for three reasons. First, it offers the best empirically documented trade-off between
perplexity degradation and memory savings, typically within \num{0.5} perplexity points of the full-precision
baseline. Second, it enables us to fit models up to \num{27}B parameters on a single \qty{80}{\giga\byte} GPU with room for a full
\num{128}K-token KV cache. Third, applying the same quantization scheme uniformly across all models ensures that
architecture and parameter count remain the only variables under test.

\subsection{Inference Configuration}

The following parameters are held constant across all models and experiments:

\begin{itemize}
  \item \textbf{Context window:} \num{131072} tokens (\num{128}K).
  \item \textbf{GPU offload:} all model layers reside on the GPU (no CPU fallback is used).
  \item \textbf{Temperature:} \num{0.0} (greedy decoding), ensuring deterministic and reproducible outputs across runs.
  \item \textbf{Maximum output tokens:} \num{2048}.
  \item \textbf{KV-cache reset:} the KV cache is fully cleared between consecutive questions,
    preventing any information leakage or prefix-caching effects that could distort timing measurements.
\end{itemize}

\section{Software Architecture}

The benchmark system is implemented as a Python package, structured using a standard \texttt{src} layout.

\subsection{Command-Line Pipeline}

The evaluation workflow is divided into six sequential stages, each exposed as an independent command-line entry point:

\begin{enumerate}
  \item \textbf{Download} - fetches the Spider and BIRD dataset archives from their official distribution channels.
  \item \textbf{Sample} - materializes sub-sampled BIRD databases to disk as standalone SQLite files,
    ensuring all downstream consumers read identical data.
  \item \textbf{References} - executes each example's gold SQL query against the appropriate database,
    producing reference answer rows persisted as newline-delimited JSON (NDJSON).
  \item \textbf{Convert} - optionally serializes all databases into all six formats and writes them to disk
    for inspection and debugging.
  \item \textbf{Benchmark} - runs one slice of the experiment (a specific model, dataset, pipeline, and set
    of formats), recording raw model outputs and timing metrics.
  \item \textbf{Score} - computes NEM, ROUGE-L, and BERTScore in a
    deferred pass over the benchmark outputs.
\end{enumerate}

\subsection{LLM Interface}

As LLM interface we have decided to use Llama Cpp, which allows us to load GGUF models directly into process memory via
the exposed bindings. This interface allows us fine grained control over all the model parameters, so we can ensure
the same conditions during all the experiment runs.

\subsection{Streaming and Timing Measurement}

The backend always streams its responses (token by token). Streaming allows TTFT to be measured from request
submission until the first output token arrives. Total model time runs from submission through completion, so it
includes TTFT and all generation after the first token.

When explicit \texttt{<think>...</think>} blocks are present, they are removed from the recorded answer before
downstream evaluation. Output-token counts and total model time cover the complete generated response.

\subsection{Serialization}

The six serialization formats defined in Chapter~\ref{ch:methodolgy} are implemented as encoder
functions, each accepting a database contents and returning a formatted string. Tables are serialized
independently and concatenated for the final output, which is used in the later stages.

\section{Dataset Preparation}

\subsection{Spider}

The Spider dataset is obtained from its official distribution
page\footnote{\url{https://yale-lily.github.io/spider}} maintained by the Yale LILY lab. We use the complete
dataset without modification: all database tables retain their full row sets, since most of the Spider's databases are
small enough to fit within the \num{128}K context window when serialized in any of the six formats.

\subsection{BIRD}

The BIRD dataset is downloaded from its official benchmark
site\footnote{\url{https://bird-bench.github.io/}}. Unlike Spider, BIRD's databases contain real-world data
with tables spanning tens of thousands of rows, far exceeding the context capacity of the evaluated models.
We therefore subsample each table to a maximum of \num{500} rows using deterministic random sampling.
Tables with fewer rows are retained in full. The cap balances two competing requirements: retaining
enough data for the reference queries to return informative results and keeping serialized databases small
enough for Direct Context Inference within the \num{128}K-token window.

Rows are sampled independently in each table, so foreign-key relationships are not guaranteed to be
preserved. We therefore execute the unchanged gold SQL queries against the sampled databases to obtain
reference answers, rather than using answers from the full databases.

The original, unsampled BIRD development split contained \num{0} empty reference results: all \num{1534}
gold queries returned at least one row on the full databases. Empty results observed after subsampling
therefore arise from the removal of rows needed to satisfy query filters or joins, rather than from empty
answers in the original dataset. We expand on the analysis of these sampling-induced empty results and
their implications for the evaluation in Chapter~\ref{ch:results}.

The sampled databases are materialized as standalone SQLite files written to disk. It guarantees that three
consumers (the serialization encoders, the reference answer generator, and the Text-to-SQL query executor),
all operate on exactly the same data.

Reducing the cap from \num{500} to \num{100} rows made more databases fit, but increased the number of empty reference
results to \num{649} (\qty{42.31}{\percent}). Increasing it to \num{1000} rows reduced empty results to \num{342}
(\qty{22.29}{\percent}), but increased mean CSV payload size by a factor of \num{1.92}. CSV and TOON then fit only \num{4} of \num{11}
databases for every tokenizer, compared with \num{6} at \num{500} rows: \texttt{financial} and
\texttt{thrombosis\_prediction} additionally exceeded the window.
These measurements support \num{500} rows as a practical compromise between retaining data and context-window
feasibility, but do not establish an optimal cap.

\section{Benchmark Execution}

\subsection{Direct Context Inference}

For the direct pipeline, the runner iterates over formats and questions. Before dispatching each question, the
runner tokenizes the complete prompt (system message plus serialized data plus user question) and checks
whether the token count exceeds the available context window  Examples that do not
fit are recorded with an explicit context exceeded marker and skipped, keeping track of which examples were attempted.

\subsection{Text-to-SQL}

For the Text-to-SQL pipeline, the model receives the database schema as data definition language statements
and must produce a valid SQLite query. The runner implements the correction policy in
Section~\ref{sec:minimalist-text-to-sql} by appending the failed response and error feedback to the conversation
as assistant and user messages, respectively. All attempts are recorded with their individual timing and
token metrics. Reported token counts and
model time accumulate across all attempts; model time includes TTFT and post-first-token generation on each
attempt, and total Text-to-SQL response latency also includes query-execution time. These measurements cover the
response workflow, not preprocessing before request submission.

\subsection{Prompt Design}

Both pipelines use deliberately minimal prompt templates. The direct inference prompt assigns the model the
role of a 'precise information retrieval assistant' with constraints to use only the provided data, output
'N/A' for missing information, and avoid conversational filler. Its complete template is reproduced in
Appendix~\ref{app:direct-prompt}. The Text-to-SQL prompt assigns the role of
a 'precise Text-to-SQL translator' constrained to output SQLite compatible SQL; its complete template is
reproduced in Appendix~\ref{app:sql-prompt}.
Both templates inject the serialized data (or schema expressed in data definition language) at a designated
placeholder. The prompts are
intentionally non-leading: we avoid few-shot examples or format-specific hints so that the model's inherent
capability remains the variable under test.

\section{Scoring Pass}
\label{sec:scoring-pass}

Accuracy metrics are computed in a separate pass. We read the raw benchmark NDJSON, join each record with its
pre-computed reference answer, and write a scored output file. The metrics follow the definitions in
Section~\ref{sec:reference-answer-metrics}:

\begin{itemize}
  \item \textbf{NEM:} applies SQuAD text normalization before exact comparison.
  \item \textbf{ROUGE-L:} records F1 from the longest common subsequence over the complete answer token
    sequences, using Porter stemming. Empty token sequences or pairs with no matching tokens receive zero.
  \item \textbf{BERTScore:} uses the English configuration (\texttt{en}) of \texttt{roberta-large}.
    Baseline rescaling is disabled. The scoring pass stores raw precision, recall, and F1; the results report F1.
\end{itemize}

SQL results and references are rendered with one row per line and cells separated by a vertical bar in column
order. Empty result sets render as empty text. For Direct Context Inference, an empty reference is instead
represented as \texttt{N/A}, matching the prompt's requested no-answer response. Before BERTScore evaluation,
blank candidate or reference texts are replaced with a full stop, to handle empty inputs in the
scoring library. This bypasses an empty-input tokenizer call that is unavailable in newer Transformers
versions, but also means that two blank texts are compared as identical full stops and can receive a
near-perfect BERTScore. NEM and ROUGE-L receive the original comparison texts.

For a failed pipeline, backend, or SQL execution with a usable reference, each enabled accuracy
metric is set to zero. Records without a usable reference are not scored; when BERTScore is
disabled, its fields are null.

Some gold queries returned empty results after BIRD subsampling. These successfully executed reference
queries were retained in the evaluation.
